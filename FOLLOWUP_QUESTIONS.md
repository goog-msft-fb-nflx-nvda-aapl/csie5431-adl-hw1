# Follow-up questions — closing the remaining gap to the challenge tier

Drafted 2026-09-17, after a full round of model and technique experimentation. We previously sent a set of general clarification questions (about using the public test labels for tuning, using external auxiliary datasets, and a couple of environment details) that haven't been answered yet. These are new, more specific questions that only make sense now that we have real numbers — not a repeat of the earlier ones, though questions 1 and 3 below build directly on two of those earlier questions. Not sent yet.

## Where we are (so the questions below have context)

Architecture (all candidates): a **language-routed ensemble** — route each example by the `language` field already given in `test.json`/`train.jsonl` (no detection needed) to a separate fine-tuned encoder per language, rather than one bilingual model. Dialogue context is dropped entirely from the input (found to hurt, not help, on both languages, at every training-data scale we tried). Per-class decision thresholds are tuned on a validation split we carved out of `train.jsonl` ourselves, never on the released public-test labels.

Three candidate configurations came out of this, all close to the challenge tier (Macro-F1 ≥ 0.82, Micro-F1 ≥ 0.83) but landing differently depending on which split we trust:

| Candidate | Chinese-route model | English-route model | Public test (Macro/Micro) | Our own validation split (Macro/Micro) |
|---|---|---|---|---|
| **A** (simplest) | MacBERT, no context, weighted BCE loss, 20 epochs | RoBERTa, no context, Asymmetric Loss, 20 epochs, lr=2e-5 | 0.8057 / 0.8238 (misses challenge tier) | 0.8502 / 0.8556 (clears challenge tier) |
| **B** (ensembled + learning-rate-tuned) | Average of two MacBERT checkpoints (different loss functions) | Average of three RoBERTa checkpoints (different learning rates) | 0.8218 / 0.8316 (clears, thin margin) | 0.8335 / 0.8442 (clears, smaller margin than A) |
| **C** (BGE-M3, found last, single checkpoint each route) | `BAAI/bge-m3`, no context, weighted BCE loss | `BAAI/bge-m3`, no context, Asymmetric Loss, lr=1e-4 | 0.8260 / 0.8273 (Macro clears, Micro just short) | 0.8605 / 0.8618 (clears, best of the three) |

Candidate B's numbers came from training about ten learning-rate/ensemble variants and picking the best-scoring one partly by checking each against the public test labels repeatedly — we're not comfortable with that as a selection method (it risks indirectly fitting to the public test set even without touching decision thresholds on it), which is part of why we haven't picked a final candidate yet.

## Questions

1. **Is Candidate B's model-selection approach a form of "using test labels" the rules mean to prohibit, or is it acceptable since it's model/hyperparameter selection rather than directly optimizing decision thresholds on the labels?** We trained about ten variants (different learning rates, different ensembles of checkpoints) and picked the best-scoring one by checking it against the public test labels repeatedly, without ever using those labels to set the per-class decision thresholds themselves. We previously asked in general terms whether using the public test labels for tuning was allowed; this is a concrete instance of that question, now that we've actually seen it produce a case where our own held-out validation split and the public test disagree about which configuration is better.

2. **Practical, not a rules question**: `BAAI/bge-m3` (a 568-million-parameter model, originally built for multilingual retrieval/embeddings, that we repurposed here as a plain text classifier) is publicly available and not trained on any intent or sales dataset, so it looks fine under the stated rules — but each fine-tuned checkpoint is about 2.2GB on disk, and using it for both the Chinese and English models would be about 4.4GB total, which is over the 4GB download budget. Is the 4GB limit meant strictly per the numbers stated, or is there any flexibility (e.g. if we convert to half precision to bring it under 4GB, or use it for only one of the two languages)?

3. **Given the measured performance gap between our Chinese-language model (around 0.86–0.87 on our own validation split) and our English-language model (around 0.84 at best, with two intent classes — "too expensive" and "compares to a competitor" — still the weakest) — would continuing unsupervised pretraining of the English model on a small, clearly-scoped public English dialogue dataset (masked-language-modeling only, no labels used at all) be within the rules' allowance for using external datasets or resources?** We're only asking about the English side here, where the extra help would matter most; we don't think it's worth pursuing for the Chinese side. We previously asked a broader version of this question about external datasets in general; this narrows it to a specific, low-risk use (unsupervised pretraining only, on one language, no labels).

4. **We found that including the prior dialogue turns consistently hurts our models' performance, on both languages, at every amount of training data we tried — dropping them and just using the current message performs best.** Before we write this up as our answer to the "does dialogue context help" report question, is this the kind of finding you'd want us to investigate further (for example, trying a more structured way of encoding the prior turns rather than just concatenating them as text) as part of the open-ended exploration section, or is reporting this negative result with supporting evidence enough?

5. **Practical question**: `run.sh` must finish within 2 hours. Our slowest tested configuration (three models averaged for English, two models averaged for Chinese) took about 21 seconds on the given 500-example public test set on an idle GPU. Is the private test set roughly the same size as the public one, or could it be substantially larger? We'd like to know how much of that 2-hour budget is actually margin before finalizing whether an ensembled configuration is safe to submit.
